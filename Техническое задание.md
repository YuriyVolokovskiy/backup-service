# ТЗ: Backup-сервис для PostgreSQL с выгрузкой в S3

## Summary

Создать минимальный микросервис на Go без веб-панели, собственной БД, RabbitMQ и Celery. Сервис по расписанию делает logical backup PostgreSQL баз через `pg_dump`, загружает dump-файлы в S3-compatible хранилище и периодически удаляет старые бэкапы по настраиваемой retention policy.

Текущий проект использует `django-dbbackup` с `PgDumpBinaryConnector`; этот connector делает binary/custom dump через `pg_dump` и восстановление через `pg_restore` согласно документации `django-dbbackup`: [docs](https://archmonger.github.io/django-dbbackup/5.3.0/databases/). В новом сервисе использовать тот же подход: PostgreSQL custom dump format.

## Key Requirements

- Язык: Go.
- Поставка: Docker image.
- СУБД v1: только PostgreSQL.
- Формат бэкапа: `pg_dump --format=custom`, файл `.dump`.
- Сжатие: использовать встроенное сжатие `pg_dump`, compression level по умолчанию `9`, так как важен минимальный размер файла.
- Restore tool: `pg_restore`.
- Конфигурация targets: YAML-файл.
- Секреты: только через env-переменные, в YAML не хранить пароли/DSN целиком.
- Хранилище: один S3-compatible bucket, разделение по `prefix` для проекта/окружения/БД.
- Cleanup: запускать периодически, retention настраивается per target.
- Уведомления: структурированные логи + Telegram bot.
- Веб-панель: не нужна.
- Автоматический restore-check: не нужен в v1.
- Если предыдущий backup конкретного target ещё выполняется, следующий запуск этого же target пропускать.

## Configuration Interface

Пример `config.yaml`:

```yaml
s3:
  endpoint: "${S3_ENDPOINT}"
  region: "${S3_REGION}"
  bucket: "${S3_BUCKET}"
  access_key_id: "${S3_ACCESS_KEY_ID}"
  secret_access_key: "${S3_SECRET_ACCESS_KEY}"
  force_path_style: true

telegram:
  enabled: true
  bot_token: "${TELEGRAM_BOT_TOKEN}"
  chat_id: "${TELEGRAM_CHAT_ID}"

defaults:
  retention:
    daily: 7
    weekly: 4
    monthly: 12
  backup_cron: "0 2 * * *"
  cleanup_cron: "0 5 * * *"
  compression_level: 9

targets:
  - id: simple-estate-prod
    engine: postgres
    database_url_env: SIMPLE_ESTATE_PROD_DATABASE_URL
    s3_prefix: simple-estate/prod/postgres
    backup_cron: "0 2 * * *"
    cleanup_cron: "0 5 * * *"
    retention:
      daily: 7
      weekly: 4
      monthly: 12
```

Пример env:

```env
S3_ENDPOINT=https://s3.example.com
S3_REGION=ru-central1
S3_BUCKET=company-backups
S3_ACCESS_KEY_ID=...
S3_SECRET_ACCESS_KEY=...

TELEGRAM_BOT_TOKEN=...
TELEGRAM_CHAT_ID=...

SIMPLE_ESTATE_PROD_DATABASE_URL=postgres://backup_user:password@host:5432/dbname
```

## Backup Behavior

- При старте сервис читает YAML, подставляет env-переменные и валидирует конфиг.
- Для каждого target регистрируются два cron job: backup и cleanup.
- Backup flow:
    - проверить, что для target нет активного backup;
    - запустить `pg_dump --format=custom --compress=9 --dbname=<DATABASE_URL>`;
    - писать dump во временный файл или streaming-upload, если реализация позволяет сделать это просто;
    - загрузить объект в S3;
    - после успешной загрузки удалить локальный временный файл;
    - отправить Telegram success/failure notification;
    - записать structured log с `target_id`, `duration`, `size_bytes`, `s3_key`, `status`.
- Имя объекта:
    - `s3://<bucket>/<s3_prefix>/YYYY/MM/DD/<target_id>-YYYYMMDDTHHMMSSZ.dump`
- Неполные uploads не должны оставаться под финальным именем. Если нужен temporary key, использовать suffix `.partial` и удалять его при ошибке.

## Cleanup Behavior

- Retention policy per target:
    - `daily`: оставить по одному backup за каждый из последних N дней;
    - `weekly`: оставить по одному backup за каждую из последних N недель;
    - `monthly`: оставить по одному backup за каждый из последних N месяцев.
- Если backup попадает сразу в несколько buckets retention, он сохраняется один раз.
- Cleanup работает только внутри `s3_prefix` конкретного target.
- Cleanup не удаляет backup, который был создан текущим активным backup job.
- Перед удалением писать log со списком удаляемых ключей.
- При ошибке удаления продолжать обработку остальных объектов и отправлять failure notification.

## CLI / Runtime Commands

Сервис должен поддерживать:

```bash
backup-service serve --config /etc/backup-service/config.yaml
backup-service backup --config /etc/backup-service/config.yaml --target simple-estate-prod
backup-service cleanup --config /etc/backup-service/config.yaml --target simple-estate-prod
backup-service list --config /etc/backup-service/config.yaml --target simple-estate-prod
```

`serve` запускает cron scheduler. Остальные команды нужны для ручного запуска и отладки без веб-панели.

## Docker Requirements

- Docker image содержит:
    - Go binary `backup-service`;
    - PostgreSQL client tools, включая `pg_dump` и `pg_restore`;
    - CA certificates;
    - timezone data.
- Контейнер запускается без root, если это не мешает работе `pg_dump`.
- `config.yaml` монтируется volume/read-only.
- Секреты передаются через env.
- Версия `pg_dump` должна быть не ниже major-версии PostgreSQL серверов, которые бэкапятся.

## Observability

- Логи в stdout/stderr в JSON или key-value формате.
- Никогда не логировать полный `DATABASE_URL`.
- Telegram уведомления:
    - success можно включать/выключать глобально;
    - failure отправлять всегда, если Telegram включён;
    - сообщение содержит `target_id`, статус, duration, размер файла при успехе, краткую ошибку при failure.
- Метрики Prometheus не обязательны в v1.

## Acceptance Scenarios

- Сервис стартует с валидным YAML и регистрирует cron jobs для всех targets.
- При отсутствующей env-переменной с DSN сервис падает на старте с понятной ошибкой.
- Ручная команда `backup` создаёт `.dump` файл в S3 по ожидаемому prefix.
- Созданный `.dump` можно восстановить вручную через `pg_restore`.
- Если backup target уже выполняется, повторный запуск этого же target пропускается и логируется.
- Cleanup удаляет только объекты внутри prefix target и сохраняет backups согласно `daily/weekly/monthly`.
- При ошибке `pg_dump`, S3 upload или cleanup сервис пишет error log и отправляет Telegram failure notification.
- В логах и Telegram не раскрывается пароль из `DATABASE_URL`.

## Assumptions

- В v1 поддерживается только PostgreSQL; MySQL/MariaDB добавляются позже отдельным engine.
- Используется простой S3 layout с обычными `.dump` файлами, не restic repository.
- Restore-check не реализуется в v1.
- Retention настраивается per target, при отсутствии значений используются `defaults`.
- Основной режим эксплуатации: Docker container с mounted YAML config и env secrets.
